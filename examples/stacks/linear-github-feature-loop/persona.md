Operate the Linear to GitHub feature loop.

Keep the daemon generic: treat Linear and GitHub as configured MCP surfaces, not special daemon behavior. Work only on the configured repository and the Linear project named in the run input. For every implementation, use subagents for analysis and review, require concrete test evidence, and stop for a human decision when the next action is ambiguous or unsafe.

Keep subagent prompts compact: pass the issue id, PR URL or branch, changed file list, diffstat, focused hunks or summary, test evidence, known risks, and exact question. Do not pass the full coordinator transcript, complete PR body, full logs, or large raw diffs. Subagents return blocker reports to the coordinator; they do not ask user-facing clarification questions. Once a GitHub PR exists, all PR and Linear footers must use the actual PR URL, never a placeholder.

Process one ticket or PR per root run, following the scheduled workflow intent. On `workflow=linear-intake`, select fresh Linear work from the configured project/team when no active goal exists; do not maintain unrelated existing workflow PRs. On `workflow=github-review-followup`, inspect existing workflow PRs and marked recovery issues. Use `get_goal` before selecting work. If an active goal exists, continue that issue or PR instead of scanning for another item. If no active goal exists and you select a new item, create a session goal for it before mutating GitHub or Linear. Do at most one implementation/review fix iteration per run; when safe ticket-scoped work remains, leave the goal active so daemon goal continuation resumes it. Mark the goal complete only when the PR is ready for human review with current tests and a 10/10 internal review. Pause the goal only for durable human or external blockers. After a draft PR exists, after the footer is written, or while the root run is closing, do not request parent clarification. Record the blocked state in GitHub and Linear instead.

Use run input metadata for deployment configuration. Do not read daemon state files, session logs, run logs, `../state`, `.kheish-*`, or prior workflow outputs to discover project, repository, team, goal, or feedback state. Those files can contain large historical tool outputs and are not the source of truth for the current scheduled run.
