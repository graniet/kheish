# Linear GitHub feature loop

This guide shows how to take the shipped `examples/stacks/linear-github-feature-loop` stack and run it for a real Linear project and a real GitHub repository.

The stack stays generic: the daemon reconciles secrets, MCP requirements, one persona, one session, one published Playbook, and two schedules. Linear and GitHub behavior lives in the MCP tools and the prompt files, not in hardcoded daemon logic.

## What the workflow does

- `linear-intake-0800-v024` looks for open Linear work in one configured project or team and starts one ticket-scoped implementation loop. Fresh intake does not require a pre-existing workflow footer.
- `github-review-followup-30m-v026` revisits draft PRs and recent workflow-marked Linear issues at `:15` and `:45`, including PR comments and stale test blockers.
- The session runs through the `linear-github-feature-pr-loop` Playbook with OpenAI `gpt-5.5` and medium reasoning by default.
- The workflow is allowed to create draft PRs early, then keep improving them until tests, review, GitHub footer, and Linear status are current.
- The model can contact the operator through `notify_operator` or `ask_operator`; Telegram is configured as a normal session reply target.

It is not a webhook listener. A new Linear ticket or GitHub PR comment is picked up at the next schedule fire, or immediately when you run `schedules trigger-now`.

## Prerequisites

From the repository root:

```bash
cargo build -p kheish-daemon
```

You also need:

- a Linear API key that can read and update the target project issues;
- a GitHub personal access token limited to the target repository, with enough rights to read code, push branches, create draft PRs, update PR bodies, and comment;
- a Telegram bot token and the numeric Telegram chat id for the human operator, if you keep operator notifications enabled;
- Docker running, because the current GitHub MCP path uses the official GitHub MCP Docker image;
- an `openai` route that can run `gpt-5.5`, either with an API key or with an imported account-backed credential.

Use a non-production Linear project or a test repository for the first run. The workflow mutates Linear and GitHub.

## 1. Choose names for this deployment

Pick a slug and keep every stateful path explicit. This prevents the common "wrong daemon / wrong state root" failure.

```bash
export STACK_SLUG=acme-web-feature-loop
export LINEAR_PROJECT="Acme Web"
export LINEAR_TEAM_KEY=ACME
export GITHUB_REPOSITORY="acme/web"
export PERSONA_ID=acme-web-feature-operator-v001
export SESSION_ID=acme-web-feature-loop-v001
export INTAKE_SCHEDULE_NAME=acme-web-linear-intake-0800-v001
export FOLLOWUP_SCHEDULE_NAME=acme-web-github-review-followup-30m-v001
export TELEGRAM_CONNECTOR=acme-web-operator-telegram
export TELEGRAM_CHAT_ID=123456789

export PORT=4025
export BASE_URL="http://127.0.0.1:${PORT}"
export RUN_ROOT=".kheish-runs/${STACK_SLUG}"
export STATE_ROOT="${RUN_ROOT}/state"
export WORKSPACE_ROOT="${RUN_ROOT}/workspace"
export AUTH_STORE_KEY_FILE="${RUN_ROOT}/auth-store-master-key"

mkdir -p "$RUN_ROOT" "$STATE_ROOT" "$WORKSPACE_ROOT"
```

For one Linear account and one GitHub account, keep the default MCP server names `linear` and `github`. If you want multiple accounts in the same daemon later, use distinct MCP server names, secret refs, persona ids, session ids, and schedule names for each account pair.

The `project` and `repository` values are prompt metadata, not an authorization boundary. Scope the real authority with a fine-grained GitHub token, Linear permissions, test projects, and separate MCP server credentials when accounts must not share access.

Linear has both Projects and Teams. If your deployment is scoped to a team, set `linear_team_key` in the Stack metadata. The intake will use that team key to list issues and will keep `project` as the human-readable deployment name.

## 2. Copy the example stack

Keep the example immutable and edit a local copy:

```bash
mkdir -p "$RUN_ROOT/stack"
cp -R examples/stacks/linear-github-feature-loop/. "$RUN_ROOT/stack/"
```

Edit `$RUN_ROOT/stack/Kheishfile.yaml`.

Change these values for your project. This example uses the shell values from step 1:

```yaml
metadata:
  name: acme-web-feature-loop
spec:
  personas:
    - persona_id: acme-web-feature-operator-v001
  sessions:
    - session_id: acme-web-feature-loop-v001
      persona_id: acme-web-feature-operator-v001
      credential_scope:
        connector_allow: ["acme-web-operator-telegram"]
        connector_credential_allow: ["acme-web-operator-telegram:bot_token"]
      reply_targets:
        - type: telegram
          connector: acme-web-operator-telegram
          chat_id: 123456789
  schedules:
    - name: acme-web-linear-intake-0800-v001
      target_session_id: acme-web-feature-loop-v001
      flow_start:
        metadata:
          project: Acme Web
          linear_team_key: ACME
          repository: acme/web
    - name: acme-web-github-review-followup-30m-v001
      target_session_id: acme-web-feature-loop-v001
      flow_start:
        metadata:
          project: Acme Web
          linear_team_key: ACME
          repository: acme/web
```

Also update the `verification` block so it checks the new persona id, session id, and schedule names. If you change the model or reasoning effort, update both the session `route_policy` and each schedule request.

If you keep Telegram enabled, replace every `feature-loop-operator-telegram` connector reference with your `TELEGRAM_CONNECTOR` value and replace the sample `chat_id`. Do not put bot tokens, webhook secrets, or private URLs in `display_name` or `communication_style`; those fields are prompt-visible.

Do not remove the explicit allow-lists unless you also understand the security impact. Empty allow-lists are not a least-privilege policy.

Do not apply the repository example file directly to a real account. Copy it, replace the sample project/repository metadata, and verify the diff before `stack apply`.

## 3. Store provider and MCP secrets

Use one auth-store master key for this `STATE_ROOT` and keep reusing it. If you lose or replace it, the daemon cannot decrypt the existing secret store.

```bash
if [ ! -s "$AUTH_STORE_KEY_FILE" ]; then
  ./target/debug/kheish-daemon secrets generate > "$AUTH_STORE_KEY_FILE"
  chmod 600 "$AUTH_STORE_KEY_FILE"
fi

export KHEISH_AUTH_STORE_MASTER_KEY="$(cat "$AUTH_STORE_KEY_FILE")"

export LINEAR_API_KEY="..."
export GITHUB_PERSONAL_ACCESS_TOKEN="..."
```

Store Linear through the built-in MCP catalog slot:

```bash
./target/debug/kheish-daemon mcp auth slots linear
./target/debug/kheish-daemon mcp auth set linear \
  --from-env LINEAR_API_KEY \
  --offline \
  --state-root "$STATE_ROOT"
```

Store GitHub in the catalog slot used by the explicit Docker MCP config:

```bash
./target/debug/kheish-daemon mcp auth set github \
  --from-env GITHUB_PERSONAL_ACCESS_TOKEN \
  --offline \
  --state-root "$STATE_ROOT"
```

If you use an OpenAI API key route instead of account-backed auth, keep `OPENAI_API_KEY` available for the daemon startup command:

```bash
export OPENAI_API_KEY="..."
```

If you use Codex account-backed OpenAI auth, import it into `openai.prod` and start the daemon with a route file that references that auth slot:

```bash
cat > "$RUN_ROOT/routes.toml" <<'TOML'
version = 1
default_route = "openai"

[routes.openai]
driver = "openai"
default_model = "gpt-5.5"
auth_ref = "openai.prod"
TOML

./target/debug/kheish-daemon secrets import-codex openai.prod \
  --offline \
  --state-root "$STATE_ROOT"
```

## 4. Write the GitHub MCP config

Linear is loaded from the built-in `planning` profile. GitHub is catalog-only today, so you own the explicit MCP server command.

```bash
cat > "$RUN_ROOT/mcp.github.toml" <<'TOML'
[mcp_servers.github]
command = "docker"
args = [
  "run",
  "-i",
  "--rm",
  "-e",
  "GITHUB_PERSONAL_ACCESS_TOKEN",
  "-e",
  "GITHUB_TOOLSETS",
  "ghcr.io/github/github-mcp-server"
]
env = { GITHUB_TOOLSETS = "context,repos,issues,pull_requests,users" }
env_secret_refs = { GITHUB_PERSONAL_ACCESS_TOKEN = "mcp.github.GITHUB_PERSONAL_ACCESS_TOKEN" }
inherit_env = false
startup_timeout_sec = 90
tool_timeout_sec = 120
TOML
```

For production, pin `ghcr.io/github/github-mcp-server` to a reviewed version or digest and narrow `GITHUB_TOOLSETS` or `GITHUB_TOOLS` if your workflow needs less surface.

Pull the image once before starting the daemon:

```bash
docker pull ghcr.io/github/github-mcp-server
```

## 5. Start the daemon

The daemon reads Linear and GitHub credentials from the secret store at MCP startup. The Stack API also uses `value_env` to compute secret drift fingerprints, so the daemon process must have `LINEAR_API_KEY` and `GITHUB_PERSONAL_ACCESS_TOKEN` exported when you later call `stack import`, `plan`, or `apply` with `--allow-secret-env`.

For an API-key OpenAI route:

```bash
./target/debug/kheish-daemon serve \
  --bind "127.0.0.1:${PORT}" \
  --state-root "$STATE_ROOT" \
  --workspace-root "$WORKSPACE_ROOT" \
  --mcp-discovery disabled \
  --mcp-profile planning \
  --mcp-config "$RUN_ROOT/mcp.github.toml" \
  --provider openai \
  --model gpt-5.5 \
  --api-key "$OPENAI_API_KEY"
```

For the Codex account-backed route from step 3, replace the last three route flags with:

```bash
  --routes-file "$RUN_ROOT/routes.toml"
```

Keep this daemon running in its own terminal. In another terminal, re-export the non-secret deployment variables from step 1. The client shell only needs `BASE_URL` and any control-plane bearer token settings for API access. Re-export `KHEISH_AUTH_STORE_MASTER_KEY` only if you run more offline secret commands against the same `STATE_ROOT`.

If your daemon uses bearer auth, also set `KHEISH_DAEMON_TOKEN_FILE` or pass `--token-file` on each CLI call.

## 6. Verify the runtime before applying

Ask the daemon what it actually loaded:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" runtime get \
  | jq '.mcp.servers[] | {server, connected, source, catalog_entry_id, uses_credentials, credential_secret_refs, error}'
```

Then check the actual tool names exposed by the loaded servers:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" runtime get \
  | jq '.mcp.tool_names'
```

You should see:

- `linear` connected from `built_in_catalog`, with `catalog_entry_id: "linear"`;
- `github` connected from `codex_config`;
- both servers using credentials;
- the MCP tool names declared in `spec.requires.mcp.tools`.

If this step is wrong, fix the daemon startup or token storage before applying the stack. `stack plan` is intentionally fail-closed when required MCP servers or tools are missing.

## 7. Configure the Telegram operator connector

The Stack configures the session reply target, but it does not create the Telegram connector. Create the connector before `stack apply`.

For a local daemon, use polling so Telegram replies can reach the daemon without a public webhook:

```bash
export TELEGRAM_BOT_TOKEN="..."

./target/debug/kheish-daemon --base-url "$BASE_URL" connectors put-telegram \
  "$TELEGRAM_CONNECTOR" \
  --file <(
    jq -n \
      --arg token "$TELEGRAM_BOT_TOKEN" \
      --argjson chat "$TELEGRAM_CHAT_ID" \
      '{
        bot_token: { value: $token },
        ingress_mode: "polling",
        polling_timeout_seconds: 30,
        ingress_events_per_second: 5,
        allowed_chat_ids: [$chat],
        include_self_output: true
      }'
  )
```

For a public deployment, use `ingress_mode: "webhook"` with a real Telegram webhook URL and secret token. Keep `allowed_chat_ids` non-empty so both inbound messages and outbound operator notifications are restricted to the intended operator.

The model does not see the chat id or bot token. It only sees that it may notify or ask the operator; the daemon resolves delivery through `reply_targets`.

## 8. Import preloaded secrets into the stack ledger

MCP needs both secrets before daemon startup. The KheishStack reconciler therefore needs to adopt those existing slots before the first apply:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" stack import \
  --file "$RUN_ROOT/stack/Kheishfile.yaml" \
  --resource secret/mcp.linear.LINEAR_API_KEY \
  --resource secret/mcp.github.GITHUB_PERSONAL_ACCESS_TOKEN \
  --allow-secret-env
```

This records ownership and salted fingerprints in the local apply ledger. It does not print or read back secret values from the daemon.

## 9. Plan, apply, and verify the stack

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" stack plan \
  --file "$RUN_ROOT/stack/Kheishfile.yaml" \
  --allow-secret-env \
  --only-changes

./target/debug/kheish-daemon --base-url "$BASE_URL" stack apply \
  --file "$RUN_ROOT/stack/Kheishfile.yaml" \
  --allow-secret-env

./target/debug/kheish-daemon --base-url "$BASE_URL" stack verify \
  --file "$RUN_ROOT/stack/Kheishfile.yaml"
```

If `plan` reports startup-only config drift for MCP routes or connector config, restart the daemon with the corrected startup flags. Do not treat that as a no-op.

Verify the operator path with a deliberately narrow run:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" sessions input \
  "$SESSION_ID" \
  --provider openai \
  --model gpt-5.5 \
  --reasoning-effort medium \
  --tool-choice specific \
  --tool-name notify_operator \
  --wait \
  "Call notify_operator once to say the Linear/GitHub workflow is configured, then confirm in one sentence."
```

You should receive the Telegram message and the run should show a delivered Telegram delivery.

## 10. Trigger the first run

The schedules will fire on their cron cadences, but the first validation should be manual. Trigger one schedule, wait until its run is complete or clearly blocked, inspect approvals/tasks, then trigger the other. `trigger-now` queues a fire for that schedule; `overlap_policy: skip` is per schedule, not a whole-session lock.

Find the schedule ids:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" --output json schedules list \
  --session-id "$SESSION_ID" \
  | jq '.[] | {schedule_id, name, status, next_fire_at_ms, in_flight_run_id, last_dispatched_run_id}'
```

Trigger intake when you want the workflow to choose a Linear issue:

```bash
INTAKE_SCHEDULE_ID="$(
  ./target/debug/kheish-daemon --base-url "$BASE_URL" --output json schedules list \
    --session-id "$SESSION_ID" \
    | jq -r --arg name "$INTAKE_SCHEDULE_NAME" '.[] | select(.name == $name) | .schedule_id'
)"

./target/debug/kheish-daemon --base-url "$BASE_URL" schedules trigger-now "$INTAKE_SCHEDULE_ID"
```

Trigger GitHub follow-up when you want it to re-read open workflow PRs and recent PR comments:

```bash
FOLLOWUP_SCHEDULE_ID="$(
  ./target/debug/kheish-daemon --base-url "$BASE_URL" --output json schedules list \
    --session-id "$SESSION_ID" \
    | jq -r --arg name "$FOLLOWUP_SCHEDULE_NAME" '.[] | select(.name == $name) | .schedule_id'
)"

./target/debug/kheish-daemon --base-url "$BASE_URL" schedules trigger-now "$FOLLOWUP_SCHEDULE_ID"
```

Do not trigger intake and follow-up back-to-back during first validation unless you intentionally want to test contention on the same session.

The shipped example offsets GitHub follow-up to `:15` and `:45`, while the daily Linear intake fires at `08:00` Europe/Paris. If the intake is still running when GitHub follow-up fires, the shared session queue and schedule overlap behavior prevent two independent agents from mutating the same workflow context at the same time.

## 11. Observe the loop

Use the control plane before inspecting state files:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" runs list \
  --session-id "$SESSION_ID"

./target/debug/kheish-daemon --base-url "$BASE_URL" approvals list \
  --session-id "$SESSION_ID"

./target/debug/kheish-daemon --base-url "$BASE_URL" tasks list \
  "$SESSION_ID"

./target/debug/kheish-daemon --base-url "$BASE_URL" sessions events \
  "$SESSION_ID"
```

In default permission mode, scheduled runs can stop on approvals when they reach mutable tools. Approve only after checking the pending tool request:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" approvals allow-all \
  --session-id "$SESSION_ID" \
  --justification "approved for this workflow run" \
  --wait
```

If a run starts local shell work, inspect the task output instead of guessing:

```bash
./target/debug/kheish-daemon --base-url "$BASE_URL" tasks output \
  "$SESSION_ID" <task_id> --full
```

## Change project or repository later

For another Linear project and another GitHub repo, make a new stack copy and change:

- `metadata.name`;
- persona id and session id;
- both schedule names and `target_session_id`;
- `flow_start.metadata.project`;
- `flow_start.metadata.linear_team_key` when the scope is a Linear team;
- `flow_start.metadata.repository`;
- the `verification` ids.

Use new schedule names when changing scheduled prompt or Playbook semantics. The current schedule API is create-oriented, so versioned schedule names make behavior explicit and avoid stale schedules pretending to be the new policy.

## Run two account pairs at the same time

For two projects that use the same Linear and GitHub accounts, two stack copies with different persona/session/schedule names are enough.

For two different Linear or GitHub accounts in the same daemon, do not reuse `linear`, `github`, `mcp.linear.LINEAR_API_KEY`, or `mcp.github.GITHUB_PERSONAL_ACCESS_TOKEN`. The built-in `planning` profile gives you one `linear` server; multiple accounts require explicit MCP config for each account. Create explicit server names and secret refs such as `linear-acme`, `github-acme`, `linear-contoso`, and `github-contoso`, then update:

- the MCP startup config;
- `spec.requires.secrets`;
- `spec.requires.mcp.servers`;
- `spec.requires.mcp.tools` if tool prefixes change;
- persona and session `mcp_server_allow`;
- persona and session `mcp_tool_allow`;
- session `credential_scope.mcp_server_allow`.

Keep each workflow on its own session. `overlap_policy: skip` prevents duplicate runs for one schedule, not cross-session contention between two unrelated workflows.

## Troubleshooting

- `Auth required` for Linear or GitHub: the secret was stored in a different `STATE_ROOT`, the daemon started with a different `KHEISH_AUTH_STORE_MASTER_KEY`, or the token was not stored before startup.
- `stack plan` cannot read `value_env`: restart the daemon from an environment that exports `LINEAR_API_KEY` and `GITHUB_PERSONAL_ACCESS_TOKEN`, then rerun with `--allow-secret-env`.
- GitHub MCP is disconnected: check Docker, image pull latency, token permissions, and the server `error` field in `runtime get`.
- `stack plan` says an MCP tool is missing: inspect `runtime get` and update the stack allow-lists to the actual tool names exposed by the loaded server.
- No PR appears immediately after a Linear ticket is created: trigger the intake schedule or wait for its cron fire.
- A GitHub PR comment is not handled immediately: trigger the follow-up schedule or wait for the next `:15` or `:45` follow-up.
- Telegram notifications work but replies do not arrive: local deployments should use `ingress_mode: "polling"`; webhook mode needs a public Telegram webhook configured outside the Stack.
- Schedules are `canceled`: you probably changed names or pruned an older ledger-owned stack. Apply the current stack and list schedules for the current session id.
- A run appears stuck: check `runs get`, `approvals list`, `tasks list`, and then `sessions events` in that order.
