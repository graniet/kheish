---
title: KheishStack
description: Reconcile daemon resources from a local KheishStack file.
---

`KheishStack` is a v1alpha1 operator format for reconciling daemon resources through the daemon control-plane API. The CLI is only a transport adapter: it reads a local file, resolves relative file references against that file's directory, and submits a self-contained manifest to the daemon. The daemon API does not read caller-local files from `soul_file`, `content_file`, or `manifest_file`.

The CLI supports:

- `kheish-daemon stack init --output-file Kheishfile.yaml`
- `kheish-daemon stack validate --file Kheishfile.yaml`
- `kheish-daemon stack plan --file Kheishfile.yaml`
- `kheish-daemon stack diff --file Kheishfile.yaml`
- `kheish-daemon stack apply --file Kheishfile.yaml`
- `kheish-daemon stack verify --file Kheishfile.yaml`
- `kheish-daemon stack import --file Kheishfile.yaml --resource kind/id`
- `kheish-daemon stack down --file Kheishfile.yaml`

v1alpha1 reconciles secrets, runtime permission/debug settings, HTTP connectors, personas, sessions, schedules, playbooks, and existence probes. It rejects fail-open capability and credential scopes by default.

## Ledger Scope

The apply ledger at `<daemon-state-root>/kheish-apply/ledger.json` is daemon-owned reconciliation state. Inspect one stack with:

```bash
kheish-daemon --base-url http://127.0.0.1:4000 stack plan --file Kheishfile.yaml
curl http://127.0.0.1:4000/v1/stacks/<ownership_id>/ledger
```

The ledger records current ownership, desired digests, secret fingerprints, and a hash-chained local operation history. Use it for daemon-local idempotence, ownership adoption, and conservative prune/down planning. It is not a remote notarized audit log and must not be treated as tamper-evident compliance history.

Do not pass a separate `--state-root` to stack commands. Start the daemon with the intended `--state-root`; the daemon API owns the ledger under that root.

## Limits

- Stack API request bodies are capped at 1 MiB. The embedded manifest is capped at 256 KiB, YAML anchors/aliases are disabled before parse, and a manifest can declare at most 512 resources.
- Only `kind: http` connectors are supported in v1alpha1, because HTTP connector live views can be compared safely without reading secret values.
- Startup-only config such as routes, MCP profiles, and connector config files is plan-only and blocks apply; it is not hot-reloaded or accepted silently.
- Schedule updates are create-only in the current daemon API. Drift on immutable schedule fields blocks apply.
- Secret values are never read back. When `value_env` is used, callers must pass `--allow-secret-env`; the ledger stores a salted fingerprint. If a secret had to be preloaded before daemon startup for MCP credential resolution, adopt it with `stack import --resource secret/<slot> --allow-secret-env` before the first apply so the reconciler does not rewrite it and disconnect already loaded MCP servers. HTTP connector secrets must use `secret_ref` or `env`, not inline `value`.
- `spec.requires.mcp.servers` and `spec.requires.mcp.tools` declare daemon startup prerequisites. `servers` accepts either names or objects with `name`, optional `source`, `catalog_entry_id`, `uses_credentials`, and `credential_secret_refs`. Stack `plan`, `apply`, and `verify` read `/v1/runtime` and fail closed when a required MCP server does not match or a required qualified tool name is absent. They do not start or hot-reload MCP; use daemon startup config for that.
- `down --yes` and prune execute supported teardown actions and skip blocked resources. Stack-managed secrets are daemon-global credentials, never deleted automatically, and remain ledger-owned until an operator explicitly handles them.
- Connector `session_policy` scopes and declared persona/session scopes are always validated fail-closed in v1alpha1. A scope family needs an explicit allow-list or `*_deny: ["*"]`; partial deny-lists are rejected because they remain fail-open in the daemon. Legacy `strict_scopes: false` and `--no-strict-scopes` inputs are accepted only as compatibility no-ops.

Schedules can declare exactly one payload: `request`, `observation_materialization`, or `flow_start`. `flow_start` stores a normal Flow start request in the schedule. Recurring Flow schedules derive a per-fire Flow id and idempotency key. One-shot Flow schedules derive both only when neither identifier is supplied; an explicit `flow_id` or `idempotency_key` is preserved without synthesizing the missing counterpart. In Stack manifests, `flow_start.playbook_ref.digest` can be omitted when the referenced Playbook version is declared in the same Stack; the reconciler resolves the immutable digest from that manifest.

## Operator Contact

Sessions can opt in to model-initiated operator contact without hardcoding a transport in the daemon. Configure normal `reply_targets` for delivery, then enable `operator` on the same session:

```yaml
spec:
  sessions:
    - session_id: feature-loop
      reply_targets:
        - type: telegram
          connector: ops-bot
          chat_id: 123456789
      operator:
        enabled: true
        display_name: Project operator
        communication_style: concise, human, and action-oriented
        allow_notify: true
        allow_questions: true
```

When `operator.enabled` is true, future runs get an `Operator Contact` system section. The model may call `notify_operator` for non-blocking updates or `ask_operator` for a blocking structured question. `operator.allow_notify: true` requires at least one deliverable session `reply_targets` entry, while `operator.allow_questions: true` can use the daemon question/resume API even without outbound delivery. The referenced output connector must already exist when the Stack does not manage that connector kind. Operator config and session `reply_targets` are topology settings: update them while the session is idle, not during an active run. The model never receives or chooses transport addresses; those remain daemon-controlled `reply_targets`. `display_name` and `communication_style` are prompt-visible, so keep them descriptive and do not put tokens, URLs, emails, chat ids, channel ids, or webhook details there. `ask_operator` uses the same durable question/resume path as normal user questions, so the original run context and session memory are preserved.

See `examples/stacks/linear-triage-daily`, `examples/stacks/playbook-review`, and `examples/stacks/linear-github-feature-loop` for runnable stacks.
