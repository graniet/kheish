# Context windows and compaction

Kheish sessions keep an append-only audit journal, but the model does not see an infinite transcript.

Before every model request, the core engine builds a provider-neutral prompt projection from the journal. That projection is the active context window. Providers such as Anthropic, Google, OpenAI, OpenRouter, and xAI then encode the same bounded projection into their native wire format.

## Core invariants

- the daemon journal remains append-only and auditable
- the model-visible prompt is rebuilt from the latest checkpoint, summary, restoration payload, and recent useful journal entries
- provider continuation state created before a prompt-window rewrite is not reused
- tool results visible to the model are bounded generically, regardless of tool name or provider
- context-window errors are classified as `context_window_exceeded` before the core retry logic runs

This is why Kheish does not need to create a fresh session for every scheduled fire. A schedule can keep targeting the same session while the session moves through multiple prompt windows. Fresh sessions are still useful for independent jobs, but they are not the main safety mechanism.

## Provider continuation

Some providers expose explicit continuation IDs. OpenAI Responses uses `previous_response_id`; Anthropic can preserve signed provider-native context blocks; other adapters may carry provider-specific message identifiers.

Kheish treats those as provider continuation state, not as durable truth. When compaction, snipping, session-memory compaction, or microcompaction rewrites the visible prompt, the core strips stale provider continuation state from the rebuilt projection.

OpenAI may resume again after a successful assistant response generated from the new window. That new `resp_*` belongs to the compacted window and can be used for later turns.

## Tool output bounds

Raw tool output is retained in the session audit. The prompt-visible representation is capped before it reaches any provider adapter.

When a tool result is too large, the model sees a structured summary with:

- `truncated: true`
- `raw_ref`
- `sha256`
- byte count
- estimated token count
- a preview

This applies to built-in tools, MCP tools, connector tools, and future tool sources. It is not tied to Linear, GitHub, or any provider-specific workflow.

## Reactive overflow recovery

If a provider still rejects a request as too large, the runtime classifies the failure as `ContextWindowExceeded`. The core then:

1. tries an aggressive prompt snip
2. if needed, creates a compaction checkpoint and summary
3. rebuilds the provider-neutral prompt
4. retries without stale provider continuation state
5. fails the run only if the rebuilt window still cannot fit

The same path handles provider messages such as OpenAI `context_length_exceeded`, provider status `413`, and equivalent prompt-too-long failures from other drivers.

## Debugging

Use debug artifacts when validating context-window behavior:

```bash
./target/debug/kheish-daemon runtime set-debug-level full
./target/debug/kheish-daemon runs debug <run_id>
./target/debug/kheish-daemon runs debug-artifact <run_id> turn-0001-attempt-0001-model-request
./target/debug/kheish-daemon runs debug-artifact <run_id> turn-0001-attempt-0001-provider-request
```

In OpenAI provider requests, a compacted main-loop retry should not contain `previous_response_id` unless the ID was produced after the latest prompt-window rewrite.
